# MeshDock 实施计划

> 依据：`docs/需求说明.md`（2026-10-17）。编写日期：2026-10-17。
> 本计划先给出动手前的实测结论，再按里程碑拆分，每个里程碑都能单独运行、单独验收。

## 0. 动手前验证结论（2026-10-17 在 lan-desktop 实测）

| # | 问题（需求第 7 节） | 结论 | 对设计的影响 |
|---|---|---|---|
| 1 | 普通权限能否执行 `tailscale set --accept-routes` | **能**。普通权限进程执行 `set --accept-routes=false`（与当前值相同，不改变任何东西）返回 0；`debug prefs` 中没有 OperatorUser 字段 | 第一版不做 UAC 提权；命令返回 “access denied” 类错误时给中文提示，并说明需要管理员 |
| 2 | 离线设备 `ping` 多久超时 | 默认约 **5.1 秒**；加 `--timeout 3s` 约 3.1 秒；在线直连约 0.1 秒 | 统一用 `ping -c 1 --timeout 3s`，外层再设 10 秒硬超时；“全部测试”并发执行，不串行 |
| 3 | 1.102 → 1.104 字段变化 | 本机只有 1.102.4，**暂时无法对比** | Rust 端所有字段都用 `Option` + `#[serde(default)]`，未知字段忽略；升级后再复测 |
| 4 | Win10 托盘效果 | **可用**（M1 实测）。32×32 图标加状态圆点，三种颜色在深色任务栏上都能分清；新托盘图标默认被 Win10 收进“^”溢出区，拖到任务栏后常驻；强杀进程会留下残影图标，正常“退出”不会 | 圆点方案保留；README 提示把图标拖到任务栏；浅色任务栏待以后有条件再看 |

另外实测发现了**需求文档没写到的情况**，需要调整判断规则：

1. **`Relay` 总是有值**。每个节点（包括本机、正在直连的 ming-pc）的 `Relay` 都是 `headscale`。它表示“归属的中继区域”，不代表当前在走中继。所以必须**先判断 `CurAddr`**，`Relay` 只用来显示经过哪里。
2. **在线但未通信的设备**：phone-router 是 `Online=true, Active=false, CurAddr=""`。按原规则会被误判成“中继”，实际上只是当前没有流量，路径未知。新增状态 **“在线·空闲”**（蓝灰色），提示“点测试查看实际路径”。
3. **时间零值**：在线设备的 `LastSeen`、未握手设备的 `LastHandshake` 是 `0001-01-01T00:00:00Z`，要当作“无”。
4. **netcheck 输出不是纯 JSON**：前面有代理日志和一行 `# Warning ...`，要从第一个 `{` 开始解析；延迟单位是**纳秒**；整条命令约 4 秒。
5. **中继区域表有 29 个**：广州自建（区域 999，`Headscale Embedded DERP`）加上 28 个官方区域。netcheck 默认只突出显示 999（实测 22.6 ms），其余折叠。设备如果走的是官方中继，也要能显示区域名。
6. 新版字段 `PeerRelay`（经另一台节点中转）当前为空，有值时显示“中继（经 节点名）”。
7. 状态顶层的 `BackendState`（实测 `Running`）和 `Health`（告警列表）用来判断托盘的整体状态。
8. **ping 走中继时退出码是 1**：输出 `pong ... via DERP(headscale) in 82ms` 后还有一行 `direct connection not established`。解析 ping 只看文本、不看退出码。（M2 实测）
9. 错误文案取自 `tailscale.exe` 1.102.4 本身：服务没运行是 `failed to connect to local tailscaled process; is the Tailscale service running?`，权限不足以 `Access denied:` 开头；控制端连不上体现在 `Health` 告警里（`Unable to connect to the Tailscale coordination server …` 或 `… hasn't received a network map from the coordination server …`）。停服务会断开组网，所以没有实测停服务，改用二进制中的原文做测试。

## 1. 技术选型

与 **VenvDock** 保持一致（都是小型托盘工具，VenvDock 已验证过 Tauri 托盘）：

| 层 | 选择 |
|---|---|
| 外壳 | Tauri 2（`tray-icon` feature） |
| 前端 | Vue 3 + TypeScript + Vite + Tailwind CSS 4 + `@lucide/vue` 图标 |
| 后端 | Rust：`serde`/`serde_json` 解析，`tokio::process` + `tokio::time::timeout` 调用 CLI |
| 插件 | `single-instance`（防多开）、`opener`；P1 再加 `notification`、`autostart` |
| 环境 | Rust 1.98.1、Node 24.14.1、pnpm 12.9.1（本机已有） |

关键实现约定：

- 调用 `tailscale.exe` 时设置 `CREATE_NO_WINDOW`，避免每 10 秒闪一次黑框。
- 路径优先 `C:\Program Files\Tailscale\tailscale.exe`，找不到再查 PATH。
- 所有 CLI 调用集中在一个模块，统一处理超时、退出码、stderr，并转成带中文说明的错误类型（原文保留，前端可折叠查看）。
- 不开任何网络端口，不保存密钥和 Token。

## 2. 目录结构（规划）

```

├─ src-tauri/src/
│  ├─ main.rs / lib.rs     启动、插件注册、单实例

│  ├─ model.rs             status / netcheck / prefs 的宽松结构体

```

## 3. 连接方式判断规则（修订版）

按顺序判断，命中即停：

| 顺序 | 条件 | 显示 | 颜色 |
|---|---|---|---|
| 1 | `Online=false` | 离线 · 最后在线 X 前（零值显示“未知”） | 灰 |
| 2 | `CurAddr` 是 192.168/10/172.16–31 | 局域网直连 | 绿 |
| 3 | `CurAddr` 带方括号（IPv6） | IPv6 直连 | 绿 |
| 4 | `CurAddr` 是其他 IPv4 | 公网直连 | 绿 |
| 5 | `CurAddr` 为空，`PeerRelay` 有值 | 中继（经 节点名） | 橙 |
| 6 | `CurAddr` 为空，`Active=true`，进入活跃不到 15 秒 | 正在打洞 | 黄 |
| 7 | `CurAddr` 为空，`Active=true` | 中继（经 广州/区域名），提示约 500 KB/s 上限 | 橙 |
| 8 | `CurAddr` 为空，`Active=false` | 在线·空闲（路径未知，点测试查看） | 蓝灰 |

- “正在打洞”靠后端记录每台设备**变为活跃的时间**来判断，status 本身分不出中继和打洞。
- 用户点“测试”后，以 ping 结果（`via DERP(...)` / `via 地址:端口`）为准，覆盖显示 30 秒。
- 区域名映射：`headscale` / 999 → “广州”；官方区域用 `debug derp-map` 里的 `RegionName`（启动时读一次并缓存）。
- 这套规则写成纯函数，用第 8 节的验收场景做单元测试。

## 4. 里程碑（P0）

每个里程碑结束时：能编译运行、自查通过、更新 CHANGELOG，再进入下一个。

### M0 项目骨架（约 0.5 天）
- `git init`，参照 VenvDock 建立 Tauri 2 + Vue 3 + Tailwind 4 工程，应用名、图标占位（不用 Tailscale 商标）。
- 窗口 960×640、可缩放，字体 `Microsoft YaHei UI` + 等宽字体，颜色变量。
- **自查**：`pnpm tauri dev` 能打开空窗口；`cargo clippy` 无警告。

### M1 托盘 + 窗口行为（约 0.5 天）
- 托盘图标（已连接 / 未连接 / 控制端连不上 三种颜色），中文右键菜单：打开主界面、刷新、在家模式、出门模式、退出。
- 关闭窗口 = 隐藏到托盘；单实例（第二次启动时把已有窗口调到前台）。
- **自查**：Win10 上看托盘图标在浅色/深色任务栏的效果（第 0 节问题 4）。

### M2 CLI 层与数据模型（约 1 天）
- `cli.rs`：执行、10 秒超时、隐藏窗口、错误归类（找不到程序 / 服务没运行 / 控制端连不上 / 超时 / 权限不足 / 其他）。
- `model.rs`：status、prefs、netcheck、derp-map 宽松解析；netcheck 去掉前缀再解析。
- `classify.rs` 及单元测试（用本机真实输出存成测试样本，样本中的公网 IP 打码）。
- **自查**：`cargo test` 通过；故意改错 exe 路径、停掉服务，确认得到对应的中文错误。

### M3 主界面：设备列表 + 自动刷新（约 1.5 天）
- 本机卡片置顶，其余设备卡片自动换行：名称、IP（点击复制）、系统图标、状态徽标、最近延迟、收发流量、最后在线。
- 每 10 秒刷新；窗口隐藏时降低频率或暂停，减少 CPU 占用。
- 加载中、空状态、出错画面（原始报错可折叠）。
- **自查**：与 `tailscale status` 逐台核对；拔网线 / 关服务看界面反应。

### M4 测速（约 0.5 天）
- 单台“测试”按钮、“全部测试”（并发，每台 `--timeout 3s`）。
- 离线设备的按钮置灰；测试中显示转圈。
- **自查**：ming-pc 直连 ~2 ms；work-laptop 离线约 3 秒内给出结果，界面不卡。

### M5 本机网络体检（约 1 天）
- 点击执行 netcheck（约 4 秒，显示进度），翻译成人话：UDP 是否可用、IPv4/IPv6 公网地址、是否对称型 NAT、到广州中继的延迟、端口映射（UPnP/PMP/PCP）。
- 官方中继区域延迟折叠显示。
- **自查**：家里应得出“有 IPv6、IPv4 不是对称型 NAT、到广州约 20 ms”。

### M6 在家 / 出门模式（约 0.5 天）
- 读 `debug prefs` 的 `RouteAll` 显示当前模式，两种模式的作用写清楚。
- 切换前确认，执行 `tailscale set --accept-routes=...`，再读一次确认结果。
- 第一版先提供手动标记“我在家”的选项（P1 再自动识别），在家却开着时显示醒目横幅，一键改回。
- 托盘菜单的两个模式项与界面同步。
- **自查**：来回切换，与 `debug prefs` 核对；结束时恢复为 `false`（在家）。

### M7 打包与收尾（约 0.5 天）
- NSIS 安装包，带图标、版本号、卸载；处理 WebView2 缺失（使用 Tauri 的 `downloadBootstrapper` 模式）。
- 中文 README、CHANGELOG；按需求第 8 节逐条验收并记录结果。
- 测量常驻内存（目标 < 100 MB）和空闲 CPU。

**P0 合计约 6 个工作日。**

## 5. P1 / P2 安排（P0 验收后再细化）

- **P1**：读默认网关自动识别在不在家（只提示不修改）→ 路径变化通知 → SSH / RustDesk 快捷按钮 → 24 小时延迟历史（本地文件）→ 主题切换 → 开机自启。
- **P2**：`up/down`（二次确认）、phone-router 健康状态、导出诊断报告（导出时要把公网 IP 打码）。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| netcheck 的 JSON 格式官方声明“不稳定” | 宽松解析，失败时显示原文；只依赖少数几个字段 |
| 判断“正在打洞”只能靠推测 | 以 ping 实测为准；界面文字写“可能” |
| 每 10 秒起一个进程，有开销 | 实测 CPU；窗口隐藏时降低频率 |
| 公司笔记本上权限可能不同 | 第一阶段不装；权限不足有中文提示，以后再加 UAC 方案 |
| Tailscale 升级改字段 | 全部字段可选；升级后用样本回归测试 |
